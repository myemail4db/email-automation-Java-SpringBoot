Why the implementation works this way

Engineering Decisions

Gmail message ID is the duplicate identity

Duplicate detection is based on the Gmail message ID rather than generated-file content. Re-exporting the same Gmail message can produce different bytes, so a file hash answers the wrong business question. Exported filenames therefore retain identity as _GMAIL-<messageId>.

Duplicates are rejected before ZIP creation

ArchiveService compares Gmail IDs in processed_review/ with IDs already present in sent_archive_email/. Previously sent messages move to duplicate/ and are excluded from the ZIP. If the same duplicate filename already exists, the new copy is preserved with _2, _3, and later suffixes instead of overwriting evidence.

Sent files and sent packages are separate

sent_archive_email/ is the authoritative record used for per-message duplicate detection. sent_archive_zip/ preserves the exact ZIP package that was successfully delivered.

Failure behavior is deliberate

If Gmail delivery fails, reviewed source files remain available and the temporary ZIP is deleted. If Gmail succeeds but a later archive step fails, the report records the partial success rather than claiming the entire operation failed before delivery.

Workflow reporting

WorkflowReport carries outcome information across Export and Send, including counts, ZIP creation, email delivery, archive results, completion state, timing, and status messages.

Testing approach

JUnit 5 and Mockito tests were used with a Red → Green → Refactor workflow for duplicate identity, duplicate-directory collision handling, ZIP archival, failed-send cleanup, and partial-success behavior. The completed lifecycle was then verified with real Gmail runs.

Java engineering improvement

The Python implementation remains the proven functional baseline. The Java version deliberately strengthens the lifecycle with Gmail-ID duplicate prevention and separate sent-email and sent-ZIP archives rather than copying every implementation detail from Python.
