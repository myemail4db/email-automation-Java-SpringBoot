Authentication guide

Gmail & OAuth Setup

Set up Google Cloud, create the desktop OAuth client, place the downloaded credentials where this application actually expects them, authorize Gmail, and verify each layer before running the full workflow.

Before you start

You need a Google account with Gmail enabled and a Google Cloud project. This application requests Gmail read-only and Gmail send access. The OAuth client type used by this project is a Desktop app.

Important: Never commit credentials.json, the generated tokens/ directory, or application-private.properties. The project .gitignore is configured to exclude them.

1. Create or select a Google Cloud project

  1. Open the Google Cloud Console.
  2. Create a new project or select the project you want to use for Email Automation.
  3. Keep this project selected while completing the remaining Google configuration.

2. Enable the Gmail API

  1. In Google Cloud, open the API Library.
  2. Search for Gmail API.
  3. Open Gmail API and select Enable.

If Gmail API is not enabled for the selected Cloud project, OAuth may succeed but Gmail API requests will not work as expected.

3. Configure Google Auth Platform

Google currently manages OAuth application settings under Google Auth Platform. Open Branding. If the platform has not been configured, select Get Started.

  1. Enter an application name, such as Email Automation.
  2. Select a user support email.
  3. Choose the audience for the application.
  4. Enter the developer/contact email requested by Google.
  5. Review and save the configuration.
Personal Gmail account? Use an External audience. While the application is in testing, open Audience → Test users and add the Gmail account that will authorize the application. Internal is intended for users inside a Google Workspace organization.

4. Review the Gmail permissions

The current Java authentication service requests these Gmail permissions:

  • Gmail read-only — used to retrieve and read messages selected for processing.
  • Gmail send — used by the outbound email stage.

For an External application, use Google Auth Platform → Data Access to configure the authorization scopes required by the application when needed by the Google Auth setup.

5. Create a Desktop OAuth client

  1. Open Google Auth Platform → Clients.
  2. Select Create Client.
  3. For Application type, select Desktop app.
  4. Give the client a recognizable name.
  5. Select Create.
  6. Download the JSON credentials file.

This application uses Google's installed/desktop application authorization flow. Do not create a Web application client for these instructions.

6. Rename and place credentials.json

Rename the downloaded OAuth client file to exactly:

credentials.json

Place it here:

email-automation-Java-SpringBoot/
└── backend/
    └── src/
        └── main/
            └── resources/
                ├── application.properties
                ├── application-private.properties
                └── credentials.json   <-- put it here
Why this exact location? GmailAuthService loads /credentials.json as a classpath resource. With the current Maven/Spring Boot layout, backend/src/main/resources/credentials.json is the source location that makes the file available at that classpath path.

Do not put it in backend/config/. The current exception text mentions a “config directory,” but the implementation actually loads the file from the classpath root.

7. Create application-private.properties

In the same resources directory, create or update:

backend/src/main/resources/application-private.properties

Use your own addresses:

email.gmail.source-account=your-gmail-address@example.com
email.send.recipient=destination-address@example.com

application.properties imports this private file with spring.config.import=optional:classpath:application-private.properties.

8. Configure the Gmail labels

The current application uses three Gmail label properties:

email.gmail.source-label=for_friend
email.gmail.success-label=for_friend/processed_review
email.gmail.fail-label=for_friend/error

Create matching labels in Gmail or change these values to labels that already exist in your account. The source label identifies the messages the workflow should process.

9. Start the application

From the backend directory:

mvn clean compile
mvn spring-boot:run

Spring Boot runs on:

http://localhost:8080

First verify Spring Boot itself:

curl http://localhost:8080/api/health

10. Trigger Gmail authorization

Call the Gmail status endpoint:

curl http://localhost:8080/api/gmail/status

On the first Gmail authorization, the application uses a local OAuth callback receiver on port 8888. Your browser should open or Google should prompt you to sign in and approve the requested Gmail permissions.

  1. Choose the Gmail account that matches your configuration.
  2. Review the permissions requested by Email Automation.
  3. Approve access.
  4. Allow the browser to return to the local callback.

11. Where the token is stored

You do not manually create the OAuth token. After successful authorization, the Google OAuth library stores authorization data in:

tokens/

The path is relative to the application's current working directory. If you start Maven from backend/, the normal location is:

email-automation-Java-SpringBoot/
└── backend/
    ├── tokens/          <-- generated automatically
    └── src/
        └── main/
            └── resources/
                └── credentials.json
Running from an IDE? The IDE can use a different working directory. If you cannot find tokens/, check the IDE's configured working directory. The code uses the relative path tokens.

12. Verify Gmail retrieval

After OAuth succeeds, test message retrieval separately from the full export workflow:

curl http://localhost:8080/api/gmail/emails

If this works, Gmail authentication, the Gmail API, the configured account, and label lookup are far enough along to proceed to export.

13. Run the export workflow

TXT:

curl "http://localhost:8080/api/export?format=text"

DOCX:

curl "http://localhost:8080/api/export?format=word"

Verification checkpoints

What are you testing?CheckIf it fails
Spring Boot/api/healthCheck Java, Maven, startup errors, and port 8080.
OAuth + Gmail client/api/gmail/statusCheck Google Cloud, credentials.json, test user, token, and port 8888.
Gmail retrieval/api/gmail/emailsCheck source account, Gmail labels, permissions, and whether messages exist.
Processing/export/api/export?format=textCheck export format, directories, retrieval, and application logs.

Start here when something goes wrong

“Resource not found: /credentials.json”

Likely cause: the OAuth client JSON is missing, has the wrong filename, or is in the wrong directory.

Fix: confirm the file is named exactly credentials.json and is located at backend/src/main/resources/credentials.json. Restart the application after correcting it.

The browser never opens or authorization does not complete

Check: first call a Gmail endpoint such as /api/gmail/status. The Gmail client is what triggers authorization. Also check the console for OAuth errors and make sure local port 8888 is available.

Port 8888 is already in use

Cause: the OAuth callback receiver is hard-coded to port 8888 in the current authentication service.

Fix: stop the process using port 8888, then retry authorization. Changing the callback port requires a code change in the current implementation.

“Access blocked,” “access denied,” or the account cannot authorize

Check: for an External app still in testing, make sure the Gmail account is listed under Google Auth Platform → Audience → Test users. Also confirm you are signing in with that same account.

“This app isn't verified”

During development, Google can display an unverified-app warning when sensitive Gmail scopes are requested. Only continue when you created/trust the Google Cloud project and understand the permissions being requested. Public distribution can require Google verification.

401 / invalid credentials / token problems

Check: confirm the OAuth client is still valid and that the generated token belongs to the intended client/account. Do not casually delete token data. If you intentionally changed OAuth clients or scopes and need to reauthorize, first stop the application, preserve anything you need for diagnosis, then remove the local generated tokens/ directory and run the Gmail authorization flow again.

403 / Gmail API request rejected

Check: make sure Gmail API is enabled in the same Google Cloud project that owns the OAuth client, and make sure the authorized account granted the permissions requested by the application.

Gmail label not found

Check: compare the labels in Gmail with email.gmail.source-label, email.gmail.success-label, and email.gmail.fail-label. Spelling and hierarchy must match the labels used by your account.

No emails are returned

Verify that /api/gmail/status works first. Then confirm the configured source label exists and actually contains messages. This separates an OAuth problem from a label/data problem.

application-private.properties is not being loaded

Confirm it is named exactly application-private.properties and placed under backend/src/main/resources/. The main properties file imports it from the classpath. It is intentionally excluded from Git, so a fresh clone will require each user to create their own local copy.

Where should I look for details?

The application writes logs to:

logs/email-automation.log

Use the log together with the verification checkpoints above to identify whether the failure is Spring Boot, OAuth, Gmail retrieval, or export processing.
